Project

Nada Vfx

Project description

Nada Vfx is my runtime vfx system for Valheim. Instead of shipping a pile of custom effects or shaders, it reuses vanilla vfx and assets that Valheim already has loaded in memory, rebuilds them at runtime, and lets you customize them. The mod aims to be lightweight, modular, and easy to extend.

Orbitals

In progress

This is the main runtime work right now. Orbitals are being moved out of the old shared setup so each effect can own its own runtime instance.

Orbs — block runtime migration

In progress

Orbs now own their typed state, visuals, motion, motion root, and follower pool. Local and dropped-item behavior are working; the last piece is making remote multiplayer use that same instance-owned path.

Remaining Orbitals — Cores, Flames, Embers

Planned

Once Orbs are done, Cores, Flames, and Embers get the same treatment as one larger pass. When that lands, the old shared Orbitals runtime should finally be able to go away.

Patterns

Planned

Give each Orbital a starting motion pattern instead of forcing everything onto the same basic loop. Things like Spiral, Helix, Figure Eight, or No Path could all be starting points.

No Path / stationary Orbitals

Planned

No Path would basically turn an Orbital into a stationary standalone effect. You could still move and rotate it, while path controls like Radius, Cycles, Speed, and Spacing would switch off.

Preserve path phase

Planned

If a bound Orbital is sitting at a specific point on its path, it shouldn't jump back to the start every time the rig is rebuilt. The goal is to remember enough path state to resume where it left off.

Length range

Planned

Bring the minimum Orbitals Length down so the same path controls are actually useful on smaller weapons and held items.

Effect stack / editor workflow

Planned

The runtime is becoming a proper building-block system, so the manager should reflect that when using the mod.

Add effects from a list

Planned

Rather than showing a full page of every effect all the time, you add the effects you actually want from a list and build the rig from there.

Duplicate, remove, and reorder effect instances

Planned

The editor should let you add the same effect more than once, tune each copy separately, remove it, and drag it around in the stack. The list order should be the runtime order.

Copy Bound Rig

Planned

Grab the vfx state from a bound weapon and load it into the editor. That makes an existing rig an easy starting point instead of something you have to recreate by hand.

Clear Effects

Planned

One button to clear the current setup instead of switching every effect off one at a time.

Public API

Planned

I think the API stays small. Other mods have the option to tell NADA what vfx state they want without needing to know anything about the editor, config entries, hierarchy, or persistence.

API goal

Planned

Other mods keep ownership of their gameplay logic. They hand NADA a resolved style or state, and NADA handles rendering, attachment, reconciliation, persistence-facing behavior, and cleanup.

Target surface

Planned

Keep the public surface boring on purpose. ^-^ Right now it just needs a few clear state-first entry points. Doesn't need to expose the whole runtime.

ApplyStyle(itemData, style) ApplyState(itemData, WeaponVfxState) Remove(itemData)

Do not expose runtime internals

Planned

Callers shouldn't need ConfigEntry objects, raw custom-data keys, rig GameObjects, hierarchy knowledge, or any of the old flat-state assumptions. Those stay internal.

Sparks

Investigating

Sparks mostly works but needs another pass to address the bits that still feel wrong in normal use.

Default emission

Planned

The default emission is just too busy right now. Bring it down so Sparks starts from a cleaner baseline.

Width / length behavior

Investigating

Lowering Width currently breaks the effect into little separated bands, almost like frets on a guitar neck, instead of simply making it narrower. Length may be doing something similar, so both need a proper look.

Strands

Investigating

Strands needs a smaller default size and a less extreme Drift response.

Baseline size

Planned

The whole Strands setup starts way too large compared with the other effects. Just need to shrink the baseline so the default is sensible.

Drift curve

Investigating

Drift basically goes from off to chaos the moment it moves above 0%. I want that curve to come in gradually. Basically what 1% does now should be the highest end behavior.

Inner + Outer Flames

Planned

Mostly a range issue: the current controls top out too early on long weapons.

Maximum flame length

Planned

Raise the max Length for both flame effects so they can actually span longer swords, polearms, and other oversized weapon shapes.

Missing visuals / alternate weapon contexts

Investigating

A lot of these aren't state bugs at all: Valheim swaps, disables, or replaces the object that's actually being rendered. NADA needs to follow the real visual instance instead of assuming the equipped object survives.

Back-slot visuals

Investigating

Bound weapons and shields can lose their rig when Valheim moves them to the character's back. That needs its own supported visual context.

Dropped weapon visuals

Investigating

Dundr is a confirmed case so far: it looks fine while equipped, then loses the rig when dropped, while the Blackmetal Pickaxe works in the same test. This probably isn't unique to Dundr, so other odd weapon prefabs need checking too. The main suspects are the dropped visual root, ItemDrop hierarchy, identity resolution, and attachment target.

Crossbows / Grappling Hook

Investigating

The Grappling Hook can bind, but its alignment is wrong, the vfx vanish during reload, and the dropped version has no rig. Crossbows likely share some of that lifecycle, so the next step is checking what Valheim swaps or disables during reload.

Throwables & Projectiles

Investigating

A bound spear loses the visible rig while it's in flight, then gets it back once it lands as a dropped item. I think throwable/projectile visuals should be treated as their own runtime context without mixing that up with the persisted state on the item.

Item lifecycle

Investigating

Upgrades losing bound state

Investigating

Upgrading the quality of a bound item wipes the rig. My guess is Valheim is replacing the underlying ItemData so almost certainly need something to carry over the saved vfx state to the upgraded item automatically.
